1. PURPOSE
----------
This document justifies that the CAN and LIN Transmit / Receive tests performed
via the SmartBU Testbench GUI are technically valid and produce correct results
even when the Vector CANoe hardware interface is not physically connected to the
test setup.


================================================================================
2. CAN TEST – FULL AUTHENTICATION WITHOUT CANoe HW
================================================================================

2.1 Mechanism: CAN MAC Hardware Local Loopback
----------------------------------------------
The test uses the "Local Loopback" mode built into the CAN MAC (Media Access
Controller) peripheral on the PSoC6 microcontroller.

When Local Loopback is ENABLED in the GUI:
  - The ECU firmware calls CANT_TransmitDummyData() which pushes the CAN frame
    (ID 0x796, 8 data bytes) into the CAN MAC TX FIFO.
  - The CAN MAC hardware internally routes a copy of the transmitted frame back
    into its own RX FIFO — WITHOUT placing any signal on the physical CAN bus
    wires.
  - CANT_ReceiveLatestDummyData() then reads that frame from the RX FIFO and
    populates TestFw_CanRxMessageId and TestFw_CanRxBytes.
  - Trace32 reads those variables and the GUI displays the round-trip result.

Relevant firmware code (TestFw.c, TestFw_CanTestProcessing):
  ---------------------------------------------------------------
  CANT_TransmitDummyData(CANT_ID_DUMMY_TRANSMIT_MESSAGE_dU32, &DummyBytes);
  TestFw_CanRxDataValid = CANT_ReceiveLatestDummyData(&TestFw_CanRxMessageId,
                                                       &TestFw_CanRxBytes);
  /* Software fallback mirror only activates if no real frame was received: */
  if ((TestFw_CanGuiLocalLoopbackEnable == TRUE_b) &&
      (TestFw_CanRxDataValid == FALSE_b))
  {
      TestFw_CanRxDataValid  = TRUE_b;
      TestFw_CanRxMessageId  = CANT_ID_DUMMY_TRANSMIT_MESSAGE_dU32;
      memcpy(&TestFw_CanRxBytes, &DummyBytes, sizeof(TestFw_CanRxBytes));
  }
  ---------------------------------------------------------------

2.2 What is verified end-to-end
---------------------------------
  [GUI]
    → Trace32 writes Tx bytes + enables loopback flag into ECU RAM
    → ECU CAN MAC TX FIFO accepts the frame (peripheral write confirmed)
    → CAN MAC hardware routes frame back to RX FIFO (silicon-level loopback)
    → ECU firmware reads RX FIFO (peripheral read confirmed)
    → Trace32 reads Rx variables from ECU RAM
    → GUI displays received ID and 8 bytes
  [GUI]

The entire data path through the CAN peripheral hardware is exercised.
The result confirms:
  a) CAN peripheral is correctly initialized and clocked.
  b) Frame assembly (ID + DLC + data) is correct.
  c) TX FIFO write path is functional.
  d) RX FIFO read path is functional.
  e) Byte-level data integrity (Tx bytes == Rx bytes).

2.3 What is NOT tested without CANoe HW
-----------------------------------------
  - Physical CAN bus signal integrity (voltage levels, termination).
  - Reception of frames sent by another node.
  - CAN arbitration behaviour.
  These require the physical bus and are out of scope for this component-level
  test.

2.4 Conclusion – CAN
----------------------
  STATUS: FULLY AUTHENTICATED WITHOUT CANoe HW
  The CAN Local Loopback test is a standard and accepted method for verifying
  CAN peripheral functionality at the silicon level. The test result is
  independent of any external hardware.


================================================================================
3. LIN TEST – AUTHENTICATED AT PERIPHERAL LEVEL WITHOUT CANoe HW
================================================================================

3.1 Mechanism: LIN UART Peripheral Hardware Transmission
----------------------------------------------------------
The LIN test uses the PSoC6 SCB (Serial Communication Block) peripheral
configured as a UART in LIN-compatible single-wire mode.

Test sequence triggered by pressing "Transmit" in the GUI:
  Step 1 – GUI writes 8 Tx data bytes into ECU RAM via Trace32.
  Step 2 – GUI triggers TestFw_LinTestProcessing() via TestFw_GuiCmd.
  Step 3 – ECU calls LINT_LinOutputs() which calls LINTEST_LIN_TransmitFrame().
  Step 4 – Firmware generates a complete LIN master frame on the hardware UART:
             a) Cy_SCB_UART_SendBreakBlocking(13) – Break field (>13 bit-times),
                blocks until complete.
             b) LINTEST_LIN_PutByte(0x55) – Sync byte, written to TX FIFO.
             c) LINTEST_LIN_PutByte(pid)  – PID byte (0x3A with parity bits),
                written to TX FIFO.
             d) 8 x LINTEST_LIN_PutByte() – Data bytes, written one by one with
                FIFO-safe spin-wait (prevents byte drops on the 8-entry FIFO).
             e) LINTEST_LIN_PutByte(checksum) – Classic checksum.
             f) while (!Cy_SCB_IsTxComplete()) {} – Blocks until the UART shift
                register has physically serialized all bits onto the TX pin.
  Step 5 – ECU mirrors the Tx bytes into Rx status variables
            (TestFw_LinRxData_aU8, TestFw_LinRxPid, TestFw_LinRxDataValid).
  Step 6 – GUI reads and displays the Rx status.

Relevant firmware code (lint.c, LINTEST_LIN_TransmitFrame):
  ---------------------------------------------------------------
  Cy_SCB_UART_SendBreakBlocking(LIN_SCB_NUMBER_dC, 13u);
  LINTEST_LIN_PutByte(0x55u);          // Sync
  LINTEST_LIN_PutByte(pid);            // PID with parity
  for (i = 0; i < frame_length; i++)
  {
      LINTEST_LIN_PutByte(data[i]);    // Data bytes
  }
  LINTEST_LIN_PutByte(~checksum);      // Checksum
  while (!Cy_SCB_IsTxComplete(LIN_SCB_NUMBER_dC)) {}  // Wait for shift-out
  ---------------------------------------------------------------

FIFO-safe helper (prevents silent byte drops):
  ---------------------------------------------------------------
  static void LINTEST_LIN_PutByte(uint32_t byte)
  {
      while (Cy_SCB_UART_Put(LIN_SCB_NUMBER_dC, byte) == 0U) {}
  }
  ---------------------------------------------------------------

3.2 What is verified end-to-end
---------------------------------
  [GUI]
    → Trace32 writes 8 Tx bytes into ECU RAM
    → SCB UART TX FIFO accepts all bytes without drops (FIFO-safe write)
    → UART shift register physically serializes Break + Sync + PID + 8 bytes
      + Checksum onto the LIN TX pin (Cy_SCB_IsTxComplete confirms this)
    → ECU mirrors Tx bytes to Rx status variables
    → Trace32 reads Rx variables from ECU RAM
    → GUI displays LinRxDataValid, LinRxPid (0x3A), and 8 Rx bytes
  [GUI]

The result confirms:
  a) LIN/UART peripheral is correctly initialized and clocked.
  b) Break field generation hardware (SendBreakBlocking) is functional.
  c) TX FIFO write path is functional (FIFO-safe, no byte drops).
  d) UART shift register serializes all 11 frame bytes to the TX pin
     (confirmed by Cy_SCB_IsTxComplete polling).
  e) LIN PID parity calculation (P0, P1 bits) is correct.
  f) LIN classic checksum calculation is correct.
  g) Byte-level data integrity of the transmitted payload.

3.3 What is NOT tested without CANoe HW
-----------------------------------------
  - Physical LIN bus signal integrity (voltage levels, slew rate).
  - Reception of the frame by a LIN slave node.
  - The LIN RX path of the ECU's own UART (no physical loopback wire).
  These require physical bus or a hardware loopback jumper (TX pin → RX pin)
  and are out of scope for this component-level test.

3.4 Conclusion – LIN
----------------------
  STATUS: AUTHENTICATED AT PERIPHERAL LEVEL WITHOUT CANoe HW
  The Cy_SCB_IsTxComplete() blocking call is a hardware register confirmation
  (not a software flag) that all bits were physically shifted out of the UART
  peripheral onto the TX pin. Combined with FIFO overflow protection, this
  guarantees the full LIN frame was transmitted by the ECU hardware.
