GLOSSARY / KEY TERMS
================================================================================
  T32 / Trace32 / Lauterbach  : Debugger tool used to connect to SmartBU ECU
                                 via SWD/JLINK probe over USB
  dbg                          : Python object representing the T32 UDP connection
                                 (t32.connect → dbg; t32.QuitTrace32 → dbg='')
  SYStem.Up / SYStem.Down      : T32 CMM commands to connect / disconnect SWD probe
  DID                          : Diagnostic Identifier — triggers firmware test actions
                                 via SendDIDGetVal_multiple_entry()
  NON_NFC (RH)                 : Right-hand handle variant without NFC chip
  NFC (LH)                     : Left-hand handle variant with NFC chip
  TimingProfile                : Frozen Python dataclass — all test wait times
                                 defined centrally in timing_profile.py
  ResetTarget()                : SYStem.Down + SYStem.Up (T32 stays alive)
  QuitTrace32()                : SYStem.Down + QUIT + taskkill + 4s USB release
  RunCode()                    : T32 "Go" command — starts ECU firmware execution
  CAPA                         : Capacitive sensor test (unlock/approach/lock)
  SG / Strain Gauge            : OpAmp-based force sensor test
  EOS                          : End-of-stroke sensor test
  BAT                          : Battery voltage monitor test (TestFw_AiBatRef)
  PSU                          : KIKUSUI programmable power supply

ISSUE 1 — CAPA Test ~30 Second Delay
Affected: NON_NFC Rev1.08 + NFC Rev1.08
File    : AutomationScripts/core/capa_test.py
--------------------------------------------------------------------------------

USER REPORT:
  The CAPA (capacitive sensor) test was taking approximately 30 seconds to
  complete even when no one was touching the sensor. This caused the full
  automation sequence to be much slower than expected.

COPILOT INVESTIGATION:
  Examined capa_test.py methods: run_tc_capa_01() and run_tc_capa_02()
  Both methods polled 6 variables via _wait_for_stable_variables():
    - TestFw_CapaUnlockSensorValue   (ADC analog value — always non-zero)
    - TestFw_CapaApproachSensorValue (ADC analog value — always non-zero)
    - TestFw_CapaLockSensorValue     (ADC analog value — always non-zero)
    - TestFw_CapaUnlockFlag          (binary flag — 0 when not touched)
    - TestFw_CapaApproachFlag        (binary flag — 0 when not touched)
    - TestFw_CapaLockFlag            (binary flag — 0 when not touched)

  ROOT CAUSE FOUND:
    _wait_for_stable_variables() had a zero-guard: any variable reading 0.0
    was treated as "not ready" and the function retried for 5 seconds per
    iteration. The flag variables (Unlock/Approach/Lock flags) are legitimately
    0 when the sensor is not being touched. This caused:
      5s timeout × multiple iterations × 2 test cases = ~30s total delay.

COPILOT FIX:
  Changed both run_tc_capa_01() and run_tc_capa_02() to only pass the 3 ADC
  sensor variables to _wait_for_stable_variables() (not the flag variables).
  Added a readings_ready early exit to break the poll loop as soon as all 3
  ADC sensor values are non-None.

  Code after fix (key section):
    SENSOR_VARS = [
        "TestFw_CapaUnlockSensorValue",
        "TestFw_CapaApproachSensorValue",
        "TestFw_CapaLockSensorValue",
    ]
    readings: Dict[str, Optional[float]] = {var: None for var in self.VARIABLES}
    sensor_readings = self._wait_for_stable_variables(SENSOR_VARS)
    readings.update(sensor_readings)
    readings_ready = all(readings.get(var) is not None for var in SENSOR_VARS)
    if sensors_active or readings_ready or time.time() >= deadline:
        break

  Also increased: capa_retry_timeout = 15.0s (from 2.0s) in timing_profile.py
  Result: CAPA test now completes in ~1–2 seconds when sensor is not touched.

ISSUE 2 — "Failed to Reset Target: Timed Out" on Manual PCB Swap
Affected: NON_NFC Rev1.08 + NFC Rev1.08
File    : Functional/trace32.py  →  ResetTarget() function
--------------------------------------------------------------------------------

USER REPORT:
  When swapping a PCB manually during testing (without using the automated
  sequence), clicking the Reset button caused the error:
    "Failed to reset target: timed out"
  The SWD probe could not reconnect to the newly inserted PCB.

COPILOT INVESTIGATION:
  Examined ResetTarget() in Functional/trace32.py.
  Original code did a single SYStem.Up call with no prior SYStem.Down:
    dbg.cmd("SYStem.Up")
  On a new/freshly inserted board, the SWD link is in an unknown state.
  SYStem.Up without first doing SYStem.Down would time out because the probe
  was still trying to use the previous board's SWD session state.

COPILOT FIX:
  Added SYStem.Down first, then a 3-attempt retry loop for SYStem.Up:

    def ResetTarget(status_label):
        global dbg
        try:
            if dbg and hasattr(dbg, 'cmd'):
                last_exc = None
                for attempt in range(3):
                    try:
                        dbg.cmd("SYStem.Down")
                    except Exception:
                        pass
                    time.sleep(0.5)
                    try:
                        dbg.cmd("SYStem.Up")
                        last_exc = None
                        break
                    except Exception as e:
                        last_exc = e
                        if attempt < 2:
                            time.sleep(1.0)
                if last_exc is not None:
                    raise last_exc
                if status_label:
                    status_label.config(text="Status: system ready", fg="blue")

  NON_NFC Rev1.08: Functional/trace32.py  →  ResetTarget()
  NFC     Rev1.08: Functional/trace32.py  →  ResetTarget()

ISSUE 3 — "Connection to Trace32 Failed" on Factory PCB Swap (Automation)
Affected: NON_NFC Rev2.00 + NFC Rev2.00 (Continous_Developement)
File    : AutomationScripts/core/integrated_automation.py
--------------------------------------------------------------------------------

USER REPORT:
  In the automated sequence, when a second PCB was placed in the fixture after
  the first test completed, the automation crashed with:
    "Connection to Trace32 Failed!!!"
  Users had to physically unplug and replug the Lauterbach USB cable to recover.

COPILOT INVESTIGATION:
  Examined integrated_automation.py — non-first-run path.
  Old code:
    if not self.is_first_run:
        t32.ResetTarget(status_label=None)   # SWD probe reset
        time.sleep(1)
        t32.RunCode(exec_label=None)          # Go
        time.sleep(2)

  ROOT CAUSE CHAIN:
    1. ResetTarget() called SYStem.Up on the stale connection from old board
    2. Old board was removed → SWD link was dead → SYStem.Up raised exception
    3. Exception was caught but T32 process had internally crashed
    4. dbg object was still non-None (pointing to crashed process)
    5. already_connected = bool(getattr(t32, 'dbg', None)) → True
    6. verify_setup(skip_connect=True) → tried to talk to dead T32
    7. Result: "Connection to Trace32 Failed!!!"

COPILOT FIX (first attempt — later revised):
  Replaced ResetTarget+RunCode with QuitTrace32 on non-first runs:
    if not self.is_first_run:
        t32.QuitTrace32(status_label=None)
  QuitTrace32 kills T32 process completely → dbg = '' → already_connected=False
  → verify_setup does full relaunch automatically.

TURN 3 — CAN/LIN LoopBack: Reduce Risk of Dead/Hung Thread
Date: April 24, 2026
Target: NON_NFC Rev2.01 + NFC Rev2.01
Files : AutomationScripts/core/test_sequences.py
        AutomationScripts/core/timing_profile.py
--------------------------------------------------------------------------------

USER:
  "CAN LIN item, ' LoopBack ' test can ? Reduce to risk of dead,,"

COPILOT ANSWER — THREE RISKS IDENTIFIED:

  RISK 1 — Stale RxDataValid flag causes false PASS:
    If TestFw_CanRxDataValid or TestFw_LinRxDataValid was left as 1 from a
    previous run, the test would immediately PASS even if the bus was dead.
    Old code never cleared these flags before sending the DID.

  RISK 2 — Fixed time.sleep(2) with no abort mechanism:
    The code always waited exactly 2 seconds regardless of:
      - Whether firmware responded in 200ms (wasteful)
      - Whether T32 had hung (would sleep 2s then block on dead read_variable)
    No deadline cap → thread could hang indefinitely.

  RISK 3 — No try/except on read_variable calls:
    Any single failed read_variable (T32 timeout/crash) would raise an
    unhandled exception and crash the entire automation thread.

COPILOT FIX — test_sequences.py _run_can_test_with_logging():

  BEFORE:
    self.adapter.set_variable("TestFw_CanGuiLocalLoopbackEnable", 1)
    self.adapter.set_variable("TestFw_KeepEcuAwake", 1)
    [set tx bytes]
    self.adapter.send_did(TestFunctionCmd.TEST_GUI_CMD_CAN_TEST_e)
    time.sleep(2)
    rx_valid  = self._as_int(self.adapter.read_variable("TestFw_CanRxDataValid"))
    rx_msg_id = self._as_int(self.adapter.read_variable("TestFw_CanRxMessageId"))
    rx_bytes  = [self._as_int(self.adapter.read_variable(...)) for i in range(8)]
    can_active  = self._as_int(self.adapter.read_variable("TestFw_CanIsActiveState"))
    fault_latch = self._as_int(self.adapter.read_variable("TestFw_CanFaultLatch"))

  AFTER:
    self.adapter.set_variable("TestFw_CanGuiLocalLoopbackEnable", 1)
    self.adapter.set_variable("TestFw_KeepEcuAwake", 1)

    # Risk 1 fix — pre-clear stale RX valid flag
    try:
        self.adapter.set_variable("TestFw_CanRxDataValid", 0)
    except Exception:
        pass

    [set tx bytes]
    self.adapter.send_did(TestFunctionCmd.TEST_GUI_CMD_CAN_TEST_e)

    # Risk 2 fix — poll with deadline instead of fixed sleep
    deadline = time.time() + TIMING.can_response_timeout  # 5.0s
    rx_valid = None
    while time.time() < deadline:
        try:
            rx_valid = self._as_int(self.adapter.read_variable("TestFw_CanRxDataValid"))
        except Exception:
            rx_valid = None
        if rx_valid == 1:
            break
        time.sleep(0.2)

    # Risk 3 fix — all reads wrapped in try/except
    rx_msg_id = None; rx_bytes = [None]*8; can_active = None; fault_latch = None
    try: rx_msg_id  = self._as_int(self.adapter.read_variable("TestFw_CanRxMessageId"))
    except Exception: pass
    for i in range(8):
        try: rx_bytes[i] = self._as_int(self.adapter.read_variable(
                 f"TestFw_CanRxBytes.dummy_byte{i}_U8"))
        except Exception: pass
    try: can_active  = self._as_int(self.adapter.read_variable("TestFw_CanIsActiveState"))
    except Exception: pass
    try: fault_latch = self._as_int(self.adapter.read_variable("TestFw_CanFaultLatch"))
    except Exception: pass

COPILOT FIX — test_sequences.py _run_lin_test_with_logging():
  Same pattern applied:
    - Pre-clear TestFw_LinRxDataValid = 0 before send_did
    - Replace time.sleep(2) with deadline poll on TestFw_LinRxDataValid
      (uses TIMING.lin_response_timeout = 5.0s)
    - All read_variable calls wrapped in individual try/except

COPILOT FIX — timing_profile.py (new constants added to dataclass + both profiles):

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------

A Windows desktop test-bench application for U-Shin's SmartBU (XNF Handle) ECU.

Purpose:
  - Connect to a Lauterbach TRACE32 debugger attached to a PSoC 4 target board
  - Flash the target ECU with either a Non-NFC or NFC firmware variant
  - Execute functional validation tests across 9 hardware features:
    LED, Battery Monitor, Motor, EOS, Strain Gauge, Capacitive Sensor,
    NFC, CAN, LIN
  - Display live measurement values in a 12-tab Tkinter GUI panel
  - Run automated test sequences and report PASS/FAIL

Technology Stack:
  - GUI       : Python 3 Tkinter + ttk (Canvas-based layout)
  - Debugger  : Lauterbach lauterbach.trace32.rcl (RCL/UDP port 20006)
  - Target MCU: Cypress PSoC 4 (PRACTICE CMM scripts)
  - Reporting : openpyxl (Excel logs)
  - Testing   : pytest
  - Launch    : .bat scripts

EXTERNAL POWER SUPPLY SETUP — OWON P4305 (for new PC / Japan colleague)
================================================================================

The OWON P4305 connects via USB and appears in Windows Device Manager as:
  "USB Test and Measurement Device (IVI)"
  under the category "USB Test and Measurement Devices"
It does NOT appear as a COM port.

Communication uses PyVISA (USBTMC transport). Required on any new PC:

STEP 1 — Install NI-VISA Runtime (required VISA backend)
  PyVISA on this laptop uses: C:\windows\system32\visa32.dll (NI-VISA)
  Download: https://www.ni.com/en/support/downloads/drivers/download.ni-visa.html
  Choose: "NI-VISA Runtime" (not the full development suite)
  Tested version: 2024 Q1 or later
